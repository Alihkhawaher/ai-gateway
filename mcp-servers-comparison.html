MCP Servers for Filesystem & Command Prompt Access

A comparison of Model Context Protocol (MCP) servers that let an AI agent read/write local files and/or execute shell commands — with explicit reasoning for each recommendation and links to every project.

Context for AI Gateway: The bundled web UI can only attach MCP servers over HTTP/S (Streamable HTTP or SSE) — the gateway does not spawn command/stdio servers. So any stdio-based server below must be bridged to HTTP first (see §5 Bridging), then added as http://localhost:/mcp with the "Use llama-server proxy" toggle enabled to bypass browser CORS.

1. Quick orientation — what "access" means

There are two distinct capabilities, often confused:

  • FILESYSTEM Filesystem access — read, write, list, search, move, delete files within (optionally) scoped directories. No ability to run programs.
  • SHELL Command prompt / terminal access — execute arbitrary shell commands, run long-lived processes, inspect running processes, interact with REPLs. This includes implicit file access (a shell can read/write anything the OS user can).

Some servers offer only filesystem access (safer); others combine both. Most "filesystem-only" servers are safer because they enforce a path allow-list and cannot execute code.

Why "best" depends on what you value — explained

🥇 Desktop Commander — best all-round for local use

Why: The most mature, actively maintained single server combining terminal + filesystem + search + diff editing. Its execute_command gives true command-prompt access, while start_process/interact_with_process let the agent run long-lived dev servers and read streaming output — something most filesystem servers cannot do. It reads Excel/PDF/DOCX directly, and edit_block applies surgical diffs instead of blind overwrites. Windows support is solid.

Trade-off: The terminal bypasses the directory allow-list, so it is effectively "give the AI your OS user's shell" — use only on a machine you trust, never in production/shared environments.

🔒 mcp-shell — best if you want isolation

Why: The only one that sandboxes in a non-root container by default. You control exactly which host folders are mounted (and whether read-only), whether it can reach the network, and which commands are allowed. This is the responsible choice when you don't fully trust the agent.

Trade-off: Requires Docker, and "filesystem access" only reaches what you explicitly mount into /workspace. It's also HTTP-native, which removes the need for a separate bridge to the AI Gateway.

🗑️ FileCommander — standout for Windows safety

Why: Its safe-delete routes deletions to the Recycle Bin/Trash (recoverable), and it uniquely handles cloud-lock files (OneDrive/Dropbox), async background search, and interactive REPLs. 47 tools in one server.

Trade-off: Newer and smaller community; stdio-only (needs a bridge for the gateway); no path allow-list sandboxing.

Why choose filesystem-only?

  • Official Filesystem is the safest option: it cannot run commands and is hard-restricted to the directories you list. Choose it when you only need structured read/write and want to avoid giving the model a shell.
  • filesystem-mcp is the best security-hardened upgrade: it adds diffing/patching and — crucially — a native HTTP mode, so it can plug into the AI Gateway directly without a separate bridge.
  • fs-mcp is notable for its human-in-the-loop editing (propose a change, review a diff in VS Code, then apply) and an HTTP server + web UI out of the box. Its run_command is a middle-ground that blocks destructive commands (rm, kill).

⚙️ fs-mcp-rs — pick this if you want a Rust "Desktop Commander"

Why: It merges a bounded terminal (with persistent sessions and process-tree kill) into a path-policy-enforced filesystem server — the closest Rust equivalent to Desktop Commander, with stricter resource bounding and an explicit separation between filesystem roots (sandboxed) and terminal commands (not sandboxed, clearly warned).

🛡️ mcp-filesystem — pick this for a hardened files-only Rust server

Why: No shell at all, strict PathTrie allow-list, read-only mode, per-tool-category opt-in, and TLS support. It's the most defensible choice if you want Rust performance with maximum safety and zero command-execution surface.

6. Concrete examples for the AI Gateway

Option A — Desktop Commander (filesystem + terminal) via supergateway

npx -y supergateway \
  --stdio "npx -y @wonderwhy-er/desktop-commander" \
  --port 8099 \
  --outputTransport streamableHttp \
  --stateful

Add in the UI: http://localhost:8099/mcp with Use llama-server proxy = ON.

Option B — Official filesystem server (safe, files only)

npx -y supergateway \
  --stdio "npx -y @modelcontextprotocol/server-filesystem C:\path\to\allowed\folder" \
  --port 8099 \
  --outputTransport streamableHttp \
  --stateful

Option C — Rust bridge (e.g. ferry) around a Rust server

# Rust-native: ferry bridges a stdio server to Streamable HTTP in one static binary
ferry serve --listen 127.0.0.1:8099 stdio -- fs-mcp-rs /allowed/folder

Option D — No bridge needed (HTTP-native)

  • filesystem-mcp: npx -y @j0hanz/filesystem-mcp --port 8099 C:\allowed\folder → add http://localhost:8099/mcp
  • fs-mcp: uvx fs-mcp . → HTTP at http://localhost:8124/mcp, Web UI at :8123
  • mcp-shell: run the Docker image → http://localhost:3333/mcp + /healthz
  • fs-mcp-rs / filesystem-mcp-rs: start in HTTP mode → http://localhost:/mcp

7. Security guidance

  • SHELL servers = giving the model your OS user's privileges. Use locally only, on a machine you can wipe, never in shared/production environments.
  • FILESYSTEM-only servers are the safer default; prefer ones with a path allow-list (official Filesystem, filesystem-mcp, mcp-filesystem, fs-mcp-rs).
  • RUST servers with run_command/terminal make the same "unsandboxed terminal" trade-off as Desktop Commander — their roots/read-only policy does not confine the shell. Read each project's warnings.
  • For any exposure beyond localhost, prefer mcp-shell (container) or add your own auth layer — most community servers ship with no authentication by default.
  • Desktop Commander's own docs warn its directory restrictions and command blocklist can be bypassed via symlinks/command substitution — treat it as unrestricted.
