# TODO — MCP pre-configuration on fresh install

Status: **Investigated, not yet implemented.** This document records the
research and the available approaches for pre-configuring MCP servers (Exa,
supergateway, etc.) so they appear automatically when a visitor first opens
the AI Gateway web UI.

## Why this isn't trivial

MCP servers configured in the bundled llama-ui are **not** stored next to the
gateway's `config.json`; they live entirely in the visitor's browser:

- The UI keeps a settings object in `localStorage`. The `mcpServers` key holds
  a JSON array of server objects:
  ```json
  [
    { "id": "...", "name": "Exa", "url": "https://mcp.exa.ai/mcp", "useProxy": false },
    { "id": "...", "name": "Filesystem", "url": "http://localhost:8099/mcp", "useProxy": true }
  ]
  ```
- This is **per-browser and per-origin**. It is unrelated to the gateway's
  server-side configuration, so adding a key to `config.json` will not
  pre-install a server for anyone.

## What the UI already does

The "Add MCP server" screen shows a **hardcoded Recommended list** baked into
the UI bundle (`webui/_app/immutable/bundle.*.js`), with icons served from
`webui/recommended-mcp/`:

| id | name | URL |
|----|------|-----|
| `exa` | Exa | `https://mcp.exa.ai/mcp` |
| `huggingface` | Hugging Face | `https://huggingface.co/mcp` |
| `github` | GitHub | `https://api.githubcopilot.com/mcp` |
| `context7` | Context7 | `https://mcp.context7.com/mcp` |

**Exa is therefore already effectively "pre-configured"** — a visitor only
needs one click to attach it. supergateway is NOT in this list.

The gateway's `/props` endpoint drives `getServerDefaults()` in the UI, but
`mcpServers` is explicitly **not** a syncable parameter (the UI strips its
`headers` on export/import and treats it as user-local), so the gateway cannot
push MCP servers through `/props`.

## Options for true pre-configuration

### Option A — Document only (no code)
Keep the current build. Point users at the Recommended list (Exa is one click)
and document the one-line supergateway command in the README.

- Pros: zero maintenance, nothing to re-apply on UI rebuilds.
- Cons: not automatic; supergateway still requires manual URL entry.

### Option B — Seed `localStorage` on first visit (recommended)
The gateway serves the UI from its own origin, so it can inject a small
bootstrap script into `webui/index.html` that, on first load, writes a default
`mcpServers` array into `localStorage` if absent. This can pre-configure Exa
and/or a `supergateway` URL for every browser that opens the gateway.

- Pros: automatic for all visitors; works with stock (unmodified) llama-ui builds.
- Cons: `webui/index.html` is regenerated by `build-webui.cmd`, so the injection
  must be applied **after** each build (add a step to `build-webui.cmd`). Needs
  a config toggle (e.g. `config.json` → `default_mcp_servers`) so the seed list
  is editable without editing the HTML each time.

Implementation sketch:
1. Add `default_mcp_servers` to `config.json` / DEFAULTS in `proxy.py`.
2. Serve that list from a tiny endpoint (or inline it into the injected script).
3. Inject a `<script>` into `webui/index.html` that reads `localStorage`,
   compares the stored `mcpServers` with the defaults, and writes any missing
   defaults (no overwrite of user edits).
4. Append the injection step to `build-webui.cmd` after the `xcopy` step.

### Option C — Fork the Recommended list (most native)
Patch the hardcoded recommended-servers array in the UI source under
`webui-src/tools/ui` to add a `supergateway` entry (name/URL/icon), then
rebuild via `build-webui.cmd`.

- Pros: native "Recommended" UX; one click, no localStorage gymnastics.
- Cons: it's a fork of llama.cpp's UI — must be re-applied after every
  `build-webui.cmd` `git pull`, and icons must be added to `webui/recommended-mcp/`.
